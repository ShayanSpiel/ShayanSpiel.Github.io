Buyer stage

Need confidence before shipping

You have an agent in development or production. You cannot reliably answer whether it works. The team is making decisions based on demos rather than systematic measurement.

Main symptoms

You know these signs

The team evaluates by running examples and checking outputs manually. Passing a demo is treated as evidence of readiness. Regressions are discovered in production. Nobody can define what good enough looks like.

Inputs required

What I need from you

Access to the agent or its traces, examples of correct and incorrect behavior, current evaluation approach if any, and a description of the workflow the agent is executing.

What is not included

Boundaries

No eval implementation in your production stack. No ongoing eval maintenance. The design package specifies what to build, how to build it, and how to calibrate it. Your team or a vendor implements the eval system.

{% include components/section-head.html tag='Evaluation types' title='What a complete eval system covers' sub='An agent is more than an LLM call. The evaluation must cover every layer of the system.' %}
Eval type

Final-output evaluation

Does the agent produce the correct answer, artifact, or action? This is the baseline but never sufficient alone.

Eval type

Task-success evaluation

Was the overall task completed successfully, regardless of the specific path the agent took?

Eval type

Trajectory evaluation

Did the agent take a reasonable path to the outcome? Correct final answers can hide expensive or dangerous intermediate steps.

Eval type

Tool-selection evaluation

Did the agent choose the right tool for each step, or did it call tools unnecessarily or in the wrong order?

Eval type

Tool-argument evaluation

Were the arguments passed to each tool valid, safe, and within expected bounds?

Eval type

Policy and authority evaluation

Did the agent respect authority boundaries, permission rules, and human approval gates?

Eval type

Cost and latency evaluation

How many tokens, calls, and seconds did the agent consume? Is the cost proportional to the value delivered?

Eval type

Regression evaluation

Do changes to prompts, tools, or the underlying model break previously passing scenarios?

Eval type

Human escalation evaluation

Does the agent escalate to a human when it should, and does it avoid escalation when it should not?

Deliverable

Evaluation goals

What the eval system must measure and why, aligned to the operational workflow.

Deliverable

Representative scenarios

A set of input-output examples covering normal cases, edge cases, and failure cases from real workflow evidence.

Deliverable

Edge cases

Boundary conditions the agent must handle, including ambiguous inputs, missing data, and adversarial conditions.

Deliverable

Rubrics

Scoring guides for human and automated evaluation that define what good, acceptable, and failing look like.

Deliverable

Deterministic checks

Checks that can be automated with code, such as tool-call validation, argument bounds, and authority compliance.

Deliverable

Model-based graders

Specifications for LLM-as-judge evaluations where deterministic checks are insufficient, including calibration criteria.

Deliverable

Human calibration process

How human evaluators are trained and calibrated to score agent outputs consistently.

Deliverable

Trajectory checks

Checks that evaluate the path the agent took, not just the destination.

Deliverable

Acceptance thresholds

Pass-fail boundaries for each eval type, calibrated against operational requirements.

Deliverable

Regression suite

A set of scenarios that must pass before every deployment, defined at the appropriate eval layer.

Deliverable

Release recommendation

A decision framework that maps eval results to release decisions: pass, conditional, or block.

Deliverable

Failure report

Documentation of what fails, how often, and under what conditions, with recommendations for improvement.
