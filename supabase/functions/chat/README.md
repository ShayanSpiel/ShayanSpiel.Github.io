## API contract (frozen — WO3 builds against this)

`POST /functions/v1/chat` with JSON:

```json
{
  "messages": [{ "role": "user", "content": "…" }],
  "locale": "en",
  "session_id": "uuid-ish-string"
}
```

Response `text/event-stream`:

```
data: {"delta":"text chunk"}\n\n
data: {"capture":true,"thanks_line":"…"}\n\n   ← at most once, after CRM write succeeded
data: {"done":true,"reply_id":"r-…"}\n\n
```

Errors: JSON `{"error":"…"}` with status `429` (rate limited), `400` (validation),
`403` (disallowed origin), `405` (non-POST/OPTIONS), `500` (upstream failure).
CORS: allowlist `https://spielos.xyz`, `https://shayanspiel.github.io`,
`http://localhost:4321`, `http://127.0.0.1:4321`; the requesting Origin is
echoed only when allowlisted.

## Capture marker protocol (v1, no Mistral tools)

The system prompt (knowledge pack §12 + the runtime addendum in `core.ts`)
instructs Mistral to emit `<<CAPTURE:name=…|email=…|company=…|needs=…|segment=…>>`
inline when a visitor shares contact details. The function scans every stream
chunk; a marker is (a) stripped from the visible reply, (b) validated
(name 2–80 chars, email regex + lowercase, company ≤120, needs ≤600, segment
must be in the pack's vocabulary else `other`), and (c) persisted before the
client sees `{"capture":true}`:

1. read-before-write dedupe on `public.leads` by email (update: fill empty
   `contact_name`, append `website_chat` to `sources`, stamp `updated_at`;
   insert: `lead_key` = email, segment classified, `best_match_workflow`
   derived from `needs`),
2. append `public.email_events` row (`event:'captured'`, `campaign:'chat-assistant'`,
   `provider:'mistral-chat'`, detail JSON with session_id/needs/locale),
3. FormSubmit email to `shayan@spielos.xyz` — fire-and-forget, 3s timeout,
   failure logged only; the CRM write is never blocked.

## Environment / secrets

Set as Supabase function secrets at deploy (WO5): `MISTRAL_API_KEY`,
`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`. Locally, `supabase functions
serve chat --env-file <path>` injects them; none are ever committed.

## Local serving (documented, optional)

`supabase/config.toml` is **not** committed by this WorkOrder. If you want
`supabase functions serve` locally, create one:

```toml
project_id = "shayanspiel-site"

[functions.chat]
verify_jwt = false
```

`verify_jwt = false` is required: the website calls the function anonymously
(no Supabase auth on the static site); the function's own CORS + rate limits
are the access control. Deploy-time equivalent: `supabase secrets set …` +
`supabase functions deploy chat --no-verify-jwt`.

## Known v1 limitations

- **Rate limit is per-isolate** (in-memory Map): Supabase may serve the
  function from multiple isolates, so the 10/min + 30/hour caps hold per
  isolate, not globally. v2: durable counters (Supabase KV / rate-limit table).
- **v1 marker capture assumes the marker is complete before the stream ends**;
  a marker truncated mid-stream is dropped (never partially leaked — the
  hold-back buffer guarantees the `<<CAPTURE:` prefix never reaches the client).
- Conversation history is client-held (v1 transient sessions, plan D13k);
  the function re-validates and caps whatever arrives (16 messages / 2000 chars).
